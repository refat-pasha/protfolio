About

Graduate developer, 2026. Focused on the parts of backend work that only fail under load — concurrency, authorization boundaries, and resource leaks.

I build production ASP.NET Core systems with Angular front ends. My flagship is CampusConnect — a university ERP covering seventeen modules and seven roles across a forty-three table schema, held up by a three hundred eighty-nine test suite at fifty-eight point six percent coverage.

The second project, a flash-sale ticketing engine, exists because I wanted to see what happens when thousands of buyers fight over two hundred seats. Double-booking is prevented with SQL Server rowversion tokens, not an in-memory lock — because an in-memory lock stops working the moment you run two API instances. A virtual waiting room admits buyers in bounded batches, and three sweeper workers reclaim seats from abandoned baskets so inventory never leaks.

Before .NET I spent three years on a learning management system that went through four backends — static HTML, Flask, PHP, then Flutter and Firebase — which is a long way of learning that the hard problems are rarely about the framework.

01

CampusConnect Flagship

ASP.NET Core MVC · Web API · EF Core · SQL Server · SignalR · xUnit

A university ERP built as an operating system for academia — 17 modules, 7 roles, 14 authorization policies, and a REST API that shares the same services as the MVC screens so the two cannot drift apart.

  • Business rules (registration, grading, fees, scheduling, exams) written as pure static classes — unit-testable with no database and no clock.
  • Uploads hardened against stored XSS, path traversal, and extension spoofing via magic-number validation.
  • Soft deletes, audit interceptors, per-user notification state, live SignalR push.
  • Dockerized with Compose; migrations and demo seeding run on first boot.

02

Flash Sale Ticketing Engine

ASP.NET Core 10 · Angular 22 · SignalR · SQL Server · Puppeteer

Cinema booking engineered for the scenario that breaks naive systems — thousands of buyers hitting one endpoint inside the same second, all fighting over the same seats.

  • Double-booking eliminated with SQL rowversion optimistic concurrency, surfaced as clean 409s.
  • Virtual waiting room: FIFO queue plus a background worker admitting bounded batches every ten seconds over SignalR.
  • Queue fairness enforced by a short-lived JWT claim, re-checked server-side — a client guard alone would be bypassable.
  • Multi-seat holds in a single transaction with partial success; three sweeper workers reclaim abandoned inventory.
  • Concurrency tests use two independent DbContexts to prove the database arbitrates, not a process lock.
